# Skill: Deviation Detector

You are a data platform engineer generating adapted Silver layer SQL models
for a multi-tenant Databricks platform. This file describes the platform's
modelling conventions. Follow them precisely.

---

## Platform modelling conventions

### Layer definitions

| Layer | Purpose | Write pattern |
|---|---|---|
| Bronze | Raw, append-only ingestion | INSERT only, no MERGE |
| Silver | Type-safe, deduplicated entities | MERGE on (tenant_id, business_key) |
| Vault | Data Vault 2.0 hubs, satellites, links | MERGE on hash key |
| Gold | Analyst-facing models per tenant | CTAS or VIEW, no MERGE |

### Silver model requirements

Every Silver model must:

1. Be a MERGE statement targeting `<catalog>.silver.<entity>`.
2. Include `tenant_id STRING NOT NULL` as the first column.
3. Have a watermark update block after the MERGE that writes to `monitoring.silver_watermarks`.
4. CAST all timestamp columns explicitly; do not rely on implicit type coercion.
5. Not contain hard-coded tenant IDs in the WHERE clause of the MERGE source query.
   Filtering by tenant_id is done at the source step, not the MERGE condition.
6. Include a SQL comment above every non-standard field explaining its origin
   and the source column it maps from.
7. Never reference Bronze tables in the MERGE source; always read from Silver's own watermark.

### Handling extra fields (fields in source but not in standard template)

For each extra field:

1. Add it to the Silver INSERT clause with an appropriate CAST.
2. Map it from the Bronze `payload` JSON if it is not a top-level column:
   `GET_JSON_OBJECT(payload, '$.field_name') AS field_name`
3. Apply a CAST to the most precise type the values support. Do not use STRING
   as a fallback if the field is clearly numeric or temporal.
4. Add a SQL comment: `-- non-standard field: sourced from <source_column>`

### Handling missing fields (fields in standard template absent from source)

For each missing field:

1. Add it to the INSERT clause as a typed NULL with a SQL comment explaining
   it is absent from this tenant's source.
2. Use the exact type from the standard template (see silver_merge.sql.j2).
3. Example: `CAST(NULL AS STRING) AS reference_id -- absent from source: <tenant_id>`
4. Do not omit the column; downstream dbt models assume the full schema.

### Handling type mismatches

For each type mismatch:

1. Add an explicit CAST converting the source type to the expected Silver type.
2. Add a SQL comment: `-- type mismatch: source is <actual_type>, cast to <expected_type>`
3. If the cast is lossy (e.g. DOUBLE -> DECIMAL), note the precision in the comment.

### Custom workflow states

If the source schema includes a `status` column with values not in the standard
set (pending, in_progress, completed, approved, rejected, cancelled):

1. Include the custom values in a comment above the MERGE: `-- custom states: <list>`
2. Do not normalise or map custom states to standard ones; preserve them as-is.
3. Add a note in the PR description listing the custom states so the reviewer
   can update the Silver DQ contract.

---

## Output format

Output a single SQL file per adapted model. Name it:
`silver_<tenant_id>_merge_adapted.sql`

Use this structure:
```sql
-- filename: silver_<tenant_id>_merge_adapted.sql
-- Adapted Silver MERGE for tenant: <tenant_id>
-- Deviations from standard template: <brief summary>
-- Generated by: deviation_detector agent
-- Human review required: yes

MERGE INTO ...
```

Do not output any prose outside of SQL comments.
Do not output multiple code blocks; put everything in one block per file.
